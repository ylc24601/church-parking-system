## 一、資訊架構：主畫面不動，新增獨立子頁

今天 `/member` 是**單一畫面**：header → 本週主日 hero → 本週停車狀態卡 → 登記本週停車 → 頁尾一句「如有停車需求或異動，請聯繫教會停車同工」（[MemberStatus.tsx:205-207](../../parking-system/app/member/MemberStatus.tsx#L205-L207)）。

**那句頁尾正是本輪要取代的東西。**

建議：**主畫面保持「本週」，資料維護放獨立子頁**。

```
/member                 本週狀態（既有）
  ├─ [!] 完整度 banner   ← 未完成時才出現，點進 M1
  └─ 「我的資料」入口卡  ← 常駐
       /member/profile   M1 我的資料＋本人確認
       /member/vehicles  M2 我的車牌
       /member/apply-p2  M3 優先停車申請
```

**為什麼不全部塞同一頁**：本週狀態是**每週**都看的，資料維護是**偶發**的。混在一起會把最常用的東西推到捲軸下面，而 LIFF 是手機 webview，第一屏很貴。

**為什麼完整度 banner 要放主畫面**：`34a` 的價值在於「有人真的去補」。只放在子頁裡等人點進去，等於沒做。

## 四、M2 `/member/vehicles` 我的車牌（`#28`＋`INV-03`）

| 狀態 | 觸發條件 | 畫面 | 規則出處 |
|---|---|---|---|
| `M2-a` 一般 | ≥1 台使用中 | 車牌列，每列「停用」（**無暱稱編輯**，走查 Q3） | `#28` |
| `M2-b` **零台** | 無使用中車輛 | **明確空狀態**：「你目前沒有登記中的車牌，將無法申請停車位」＋大顆「新增車牌」 | `#28` Decision |
| `M2-c` 停用最後一台 | 按下最後一台的停用 | **二次確認**：「停用後你將無法申請停車位，可隨時重新新增。」→ 允許 | `#28` Decision |
| `M2-d` 該車有未結束預約 | `pending`/`approved`/`temp_approved`/`waiting`/`released_late` | **擋住**並說明原因（要先取消本週預約）——**這條不因零台決定而放寬** | `0038` `unfinished_reservations` |
| `M2-e` 新增撞到他人 | 該車牌目前由別人使用中 | 「此車牌目前由其他會友使用。若是家人共用的車，請先請對方在自己的頁面停用，或洽同工協助」——**不出現姓名** | `#28`／`active_plate_owned_by_other` |
| `M2-f` 新增自己停用過的 | 自己有該車牌的歷史列 | 不是新增，是**恢復**；畫面直接呈現為「重新啟用」 | `0038` `inactive_plate_exists` |
| `M2-g` 已停用清單 | 有歷史列 | 摺疊區「已停用的車牌」＋「重新啟用」 | `INV-03` soft delete |

**夫妻共車換手的完整走查**（這是推翻「至少留一台」的那個案例，必須全程可自助）：

```
先生 M2-a（ABC-1234） → 停用 → M2-c 二次確認 → 先生 M2-b（零台）
太太 M2-b → 新增 ABC-1234 → 成功（她若曾持有 ⇒ M2-f 恢復）
換回去：太太停用（M2-c）→ 先生 M2-g 重新啟用
```

**⚠️ 走查重點**：中間那個窗口——先生已停用、太太還沒加——兩邊都是零台。這是**可接受的**（他們自己會發現，因為申請不了），但 `M2-b` 的文案必須讓「為什麼我不能申請」一眼可解釋。

## 五、M3 `/member/apply-p2` 優先停車申請（`#11`）

| 狀態 | 觸發條件 | 畫面 | 規則出處 |
|---|---|---|---|
| `M3-a` 空白表單 | 無未決申請單 | 事由**可複選**；勾選後才展開該事由要的欄位 | `#11` Constraints |
| `M3-b` 條件欄位 | 勾「幼兒同行」 | 孩童**姓名＋生日**（可多筆、非必填滿）；勾「行動不便」→ 行動不便者姓名；勾「長者同行」→ 長者姓名＋生日 | `eligibility_dependents`（`0020`） |
| `M3-c` 已送出 | 有未決申請單 | 「審核中」＋送出時間＋「重新送出會取代這一筆」 | `#11` `superseded_count` |
| `M3-d` 已有資格又送新申請 | 目前 P2 有效 ＋ 送出新申請單 | **必須明說**：「送出申請不會影響你目前的資格，覆核後才會變更」 | `INV-01` |
| `M3-e` 核准後 | 覆核者核准 | 顯示現行資格與**效期到期日**（永久型寫「長期有效」）；**不顯示**覆核者是誰、也不顯示 `review_note` | 隱私姿態（#12）／走查 Q1 |
| `M3-f` 退回 | 覆核者退回 | 只顯示「已退回」＋可重新送出；**不顯示理由、不推播** | 走查 Q2 |

**⚠️ 兩個最容易被畫成同一件事的東西：**

| | 每週同行宣告（**已存在**） | P2 資格申請（**本輪新增**） |
|---|---|---|
| 在哪 | `/member` 登記表單裡的核取方塊 | M3 獨立表單 |
| 問什麼 | 「**本週**有年長者／學齡前幼兒同行」 | 「我**符合**幼兒同行這項資格」 |
| 寫到哪 | 本週那筆 reservation 的 `effective_priority` | `user_eligibility`（且**只有覆核者能寫**） |
| 出處 | [MemberStatus.tsx:506-519](../../parking-system/app/member/MemberStatus.tsx#L506-L519) | `#11` |

**把這兩件事畫成同一個勾選框，會讓會友以為勾了就有資格**——而資格其實要人覆核。

**⚠️ 眷屬要收姓名，不是只收生日**（2026-08-10 使用者提問後更正）：`eligibility_dependents.dependent_name` 是 **`NOT NULL`**（[0020:12-20](../../parking-system/supabase/migrations/0020_member_import.sql#L12-L20)），匯入器也在收 `child_1..3` 的姓名（[memberImport.ts:174](../../parking-system/lib/memberImport.ts#L174)）。只收生日的話：**那一列建不出來**／**本人送的資料比同工代填還少**（正好違背 Epic 的目的）／**覆核者「憑認識」時沒有東西可對**（生日對不上任何人）。三種眷屬（`impaired`／`child`／`elder`）在 schema 裡是同一個形狀，表單不該只對其中一種收姓名。

**效期與名單是兩件事**：效期只由**最小的孩子**決定（`p2_child_birthdate` 單一值），但**眷屬名單本身是一對多**。所以表單允許多筆、hint 寫「其他孩子可以不填」——填得下，但不逼他交出全家的生日。

**⚠️ 複選事由的可見後果**：每週宣告的核取方塊今天由**單一** `apply.companionKind` 驅動（同上出處），因為 canonical 是一人一事由。所以即使 M3 能複選、申請單完整保存，**核准後本週宣告仍只會出現一種**。這是 `#31` 未解時的正常表現，不是 bug——但 M3 的送出成功畫面不該讓人期待「兩種都會出現」。

## 七、走查已定（2026-08-09）

**Q1 ⇒ 顯示 P2 效期到期日。** M1 的資格區塊要寫出「有效至 YYYY/MM/DD」（幼兒同行會在某年 8/31 到期）。理由：到期日是他自己的事，突然失去優先權而不知道為什麼更糟。**永久型事由**（行動不便長期／長者同行）沒有到期日，此時寫「長期有效」而不是留白——`validUntil = null` 在系統裡的意思是 `permanent`，不是「未設定」。

**Q2 ⇒ 理由不給會友看；改成幹事端的流程護欄。**
`review_note` **維持單一內部欄位、不拆兩欄**。會友端只看到「已退回」，理由由**人**告訴他。
⇒ **幹事端待做（記在此，實作屬覆核頁那一份）**：按下「退回」之前，畫面要提醒「**請先與當事人溝通後再退回**」。系統的退回是**溝通結果的紀錄**，不是通知手段。
⇒ 連帶：M3-f 不需要顯示任何理由欄位；也**不要**送「你的申請已被退回」這種推播——那正好是「讓系統代替人開口」。

**Q3 ⇒ 車牌暱稱不做。** M2 只做新增／停用／恢復。
⚠️ **連帶發現**：`vehicles.nickname` 這個欄位**目前沒有任何寫入路徑**——`0001` 建了它，[MemberStatus.tsx:501](../../parking-system/app/member/MemberStatus.tsx#L501) 與 `app/admin/members/[id]/MemberVehicles.tsx:115` 都在渲染它，但除了 dev seed 之外沒有東西寫得進去 ⇒ 在 production 它恆為 null，那幾處渲染都是走不到的路。**本輪不處理**，但這是一筆該清的帳（要嘛給它 writer，要嘛拿掉渲染）。

**Q4 ⇒ 手機變更延後。** M1 的手機欄位本輪就是**唯讀＋「如需變更請洽同工」**；變更請求（提出 → admin confirmation → update identity）排到 `#11` 那一組，與覆核 inbox 一起做——反正都要覆核。
